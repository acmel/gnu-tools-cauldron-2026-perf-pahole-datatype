What this is about?



  • Two views of a struct, disconnected
  • perf: the dynamic view (who touches what)
  • pahole: the static view (where it sits)
  • Gluing them: JSON + CTF
  • What the glue found (bugs!)
  • False sharing, end to end

pahole: the static view


  • Which fields fall on which cacheline
  • Holes, padding, --reorganize suggestions
  • Knows nothing about runtime access

perf data-type profiling


  • Namhyung Kim, merged v6.8, full in v6.10
  • typecln sort key in v6.12
  • Each sampled load/store resolved via BTF + DWARF
  • Per-byte-offset histogram: counts + periods

The pipeline



  perf mem record -a --sample-cpu -- ./workload
  perf report -s type,typeoff --hierarchy -i perf.data
  # NEW: machine-readable export for pahole
  perf report -s type --data-type-json=profile.json -i perf.data
  pahole --perf-data-type=profile.json vmlinux
  # per-sample analyses (false sharing, group hints):
  perf data convert --to-ctf=ctf.dir --data-type -i perf.data
  pahole --perf-data-type=ctf.dir vmlinux

What a sample tells us today


  • Sample lands on an instruction
  • Memory operand resolves to (type, offset)
  • Type + offset resolves to the member
  • Histogram over members that were sampled
  • Never sampled = absent
  • "no samples" vs "never accessed"

Around the sampled read


  • A sample comes with an IP
  • Instructions around it touch other members
  • Typically the same cacheline: the working set
  • Today: discarded, only the sampled operand counts

"Sampling" members with no samples


  • Walk the basic block from its entry...
  • ...up to the first branch after the sample
  • All of it executed: guaranteed, not guessed
  • Backwards too
  • reaching the IP executed the block entry..IP

  movl 0xe8(%rbx), %eax   ; +232 sk_ll_usec <- inferred, never sampled
  ...
  movl 0xf4(%rbx), %edx   ; +244 sk_rcvbuf  <- SAMPLED (PEBS/IBS here)
  ...                     ; straight-line: all executed
  jne  .slow_path         ; first branch: stop here

The parity check pays off


i7-14700K, PEBS, 287,278 resolved samples in 22 members:


              CTF (per-sample)              JSON (aggregate)
  saddr   36489 R +   1 W = 36490      36490 R, 0 W
  daddr   36921 R +   8 W = 36929      36929 R, 0 W
  • Nine samples out of 287,278
  • Arithmetic exact: same samples, opposite direction

Two sources of "store?"


  • JSON path: instruction parser
  • operand in target slot = store
  • CTF path: sample->data_src
  • what the hardware said
  • cycles captures carry no data_src: agree
  • Only memory-event captures expose the drift

Verdict: the samples are broken


  • Store-event samples, store ran in kernel
  • VMAP-stack address in the sample
  • PEBS ip fixup failed: IP = interrupted userspace load
  • JSON reports the IP's direction (LOAD)
  • CTF overrides with data_src (STORE)
  • Fix: classify direction once, in the resolver
  • event -> data_src -> parser

The test that found a bug nobody knew about


  • Operand-equality test written to drop those nine
  • Next capture: flagged 132,819 samples
  • 72% at plain disp(%rip) sites, patched at boot
  • _raw_spin_unlock alone ~50% of bad_addr

Statically call *pv_ops_lock+0x8(%rip)...


  • One fixed operand address: the pv_ops pointer
  • At runtime: native per-instance unlock store
  • 28 distinct addresses = per-cpu lock instances
  • Every store attributed to pv_ops: never touched!
  • A bogus attribution looks like a good one

bad_addr is a metric



How much of a kernel profile is being disassembled from text that never executed.

Two classes of drops


  • Failed PEBS IP fixup (the nine, hand-verified)
  • Static vs runtime text
  • alternatives-patched sites (the bulk)
  • Both: the recorded IP's disassembly
  • doesn't describe the access
  • Dropping is right in both cases

Fix direction: REPORTED


  • Kernel emits PERF_RECORD_TEXT_POKE
  • for live patches
  • machine__process_text_poke()
  • updates the DSO data cache
  • capstone/LLVM backends read through that cache
  • Boot patches: synthesize records at record start
  • Enumerate patch-site marker symbols
  • not section names

Fix direction: PROPOSED


  • The DSO cache is a single mutable snapshot
  • Post-hoc annotation sees only the FINAL generation
  • Per-generation attribution needs
  • poke history + sample time
  • Intel PT has this (incremental decode)
  • data-type path doesn't
  • This part is a proposal, not a report

Open thread


  • Remaining ~28% of bad_addr
  • register-operand sites
  • User/kernel IP split needs its own attribution pass
  • objdump backend reads vmlinux directly
  • never sees pokes

False sharing, step by step


  • perf's own false_sharing workload
  • Told as a TCP connection: net_conn, 64-byte aligned
  • Built to collide, fails closed
  • skip, never false negative

The fixture layout


  • cacheline 0: identity + rx counters
  • the false-sharing line
  • cacheline 1: tx + congestion control
  • true-sharing control
  • cacheline 2: connection config, shared reads only
  • Readers checksum identity
  • writer updates counters, same instance

The chain



  perf mem record --sample-cpu -o fs.data -- \
      perf test -w false_sharing <s> <nreaders>
  perf data convert --to-ctf --data-type -i fs.data --force fs.ctf
  pahole -F dwarf --perf-data-type=fs.ctf -C net_conn $(command -v perf)
  • net_conn lives in the perf binary: build ID verified

What the detector prints



  >>> FALSE SHARING: cacheline 0: saddr / packets_rx
  >>> GROUP (true sharing): mss / snd_wscale -- consider same cacheline
  • Same instance, distinct CPUs, a write, inside 10us
  • Lines 1 and 2 silent
  • Plus GROUP (true sharing) hints
  • for co-accessed members

Difficulty: reliable collision


  • Threads pinned to distinct CPUs
  • Fields volatile
  • or the compiler keeps them in registers
  • Nothing collides: test skips, never asserts a negative

Difficulty: honest grading


  • PEBS/IBS addr + CPU identity → CONFIRMED
  • perf record -d fallback → SUSPECTED
  • The hardware decides how sure pahole may be

Difficulty: the direction bug


  • mem-stores samples classified as loads
  • x86 parser vs hybrid E-core latency path
  • Settled: event -> data_src -> parser
  • once, in the resolver
  • JSON and CTF producers cannot disagree

The dropped samples are the story


  • bad_addr 132,819 == converter Skipped 132,819
  • JSON total == converter Resolved
  • pahole JSON/CTF byte-identical on resolved types
  • Drops make the verdicts trustworthy

struct sock: logical != aligned


  • __cacheline_group markers pack without padding
  • Write tail + read head share hardware cachelines
  • Fix exists: __cacheline_group_begin_aligned()
  • struct sock hasn't adopted it (full story at LPC)

Use case: struct sock cacheline groups



  $ pahole -C sock vmlinux
  struct sock {
          struct sock_common         __sk_common;          /*     0  0x88 */
          /* --- cacheline 2 boundary (128 bytes) was 8 bytes ago --- */
          __u8  __cacheline_group_begin__sock_write_rx[0];
          atomic_t                   sk_drops;             /*  0x88   0x4 */
          __s32                      sk_peek_off;          /*  0x8c   0x4 */
          struct sk_buff_head        sk_error_queue;       /*  0x90  0x18 */
          struct sk_buff_head        sk_receive_queue;     /*  0xa8  0x18 */
  • Fields of the same hot path share a cacheline
  • rx/tx, read-mostly vs read-write: six groups
  • 2016: sk_drops moved away: UDP flood +20%
  • 2024: sk_peek_off moved for TCP SO_PEEK_OFF
  • TCP_RR: +4-5%

Caveats


  • Inferred entries carry no period: flagged, kept apart
  • Loops: per-anchor-execution guarantees
  • Calls: stop at first branch (any branch), conservative
  • Blocks are the unit
