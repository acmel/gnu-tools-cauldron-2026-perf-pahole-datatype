  • The annotation TUI navigates it: jumps, calls
  • Namhyung: parse memory operands too
  • ...and data-type profiling is built on it
  • Backends today: objdump, capstone, LLVM
  • Each has issues: arm64 needed capstone/LLVM fixes
  • We want all three: compare their outputs in CI

How a sample becomes a type


  • Sample IP → instruction → memory operand
  • PC-relative or absolute: the global variable
  • Else: DWARF variable in that register, by scope
  • Else: replay basic blocks up to the sample
  • x86 and PowerPC; arm64 in review
  • DWARF variables seed register and stack types
  • No luck? Widen the scope and replay again
From tools/perf/util/annotate-data.c: find_data_type_die() does the direct DWARF match, find_data_type_block() builds basic blocks from each scope start to the sample, innermost scope first, and find_data_type_insn() replays them with update_var_state()/update_insn_state(). percpu: %gs-relative immediates and a tracked percpu base, looked up in DWARF globals. arch_supports_insn_tracking(): x86 and PowerPC only today.

Patch 20 fixes a stale stack state bug in x86 found along the way: each port improves the others. With compiler access records, none of these idioms would need teaching.

What a sample tells us today


  • Sample lands on an instruction
  • Operand → (type, offset) → member
  • Histogram over members that were sampled
  • "No samples" is not "never accessed"
  • Instructions around the IP touch other members
  • Typically the same cacheline: the working set
  • Today: discarded, only the sampled operand counts

Idea: "sampling" unsampled members


  • Not implemented yet: an idea
  • Walk the basic block from its entry...
  • ...up to the first branch after the sample
  • All of it executed: guaranteed, not guessed

movl 0xe8(%rbx), %eax   ; +232 sk_ll_usec <- inferred, never sampled
...
movl 0xf4(%rbx), %edx   ; +244 sk_rcvbuf  <- SAMPLED (PEBS/IBS here)
...                     ; straight-line: all executed
jne  .slow_path         ; first branch: stop here

Inferred accesses: type vs instance


  • Same base register, unchanged: same instance
  • Its data address follows: sample addr ± offsets
  • Those can feed false sharing and co-access
  • Other base registers: other objects, no address
  • Those give type coverage only
  • Period: same executions, not same event cost
Not implemented yet. An access through the same base register as the sampled one, with the register unchanged in between, is the same object: its data address is the sampled address adjusted by the difference in displacement, so it can take part in instance-based analysis (false sharing, co-access on the same instance). Accesses through other registers touch other objects whose address we do not have: they only add to type coverage. Period: an inferred access in the same straight-line block executed as often as the sampled one, so the sample period transfers as an execution count. It does not transfer as event cost: with mem-loads,ldlat=30 the sampled load qualified, the inferred one may not have (often it hits the line the sampled access brought in), and the latency weight belongs to the sampled instruction only.

What compilers give us today


  • -Wpadded, and struct layout dumps in both
  • No profile-driven struct layout upstream
  • GCC had struct reorg once: what did we learn?
  • BOLT/AutoFDO/Propeller: code, not data layout
  • LLVM alias info: typed accesses, not emitted
  • MemProf: heap; RFC: vtables for PGO
  • Native targets: no per-instruction type records
Type-based alias info: loads/stores carry base type, access type and offset in LLVM, used for optimization and not written to the binary; ask whether GCC has an equivalent. Dynamic type profiling RFC: Mingming, Teresa, David, Snehasish (Google), Nov 1 2023, https://discourse.llvm.org/t/rfc-dynamic-type-profiling-and-optimizations-in-llvm/74600, instrumentation-based, for indirect call promotion.

Reconstruction has a ceiling


  • Optimized code: DWARF loses register variables
  • Branches and loops blur what a register holds
  • Several candidates? Heuristics pick one
  • container_of offsets, casts, void *: no type
  • Needs full DWARF: production kernels ship BTF
  • Per arch: arm64 tracking is 15 patches
  • find /: unknown for 17.95% loads, 27.49% stores
is_better_type() in annotate-data.c is the heuristic; update_var_state() handles container_of only for offset 0 (the copy-back case). perf data-type profiling does not use BTF today (no BTF in annotate-data.c). Globals and percpu variables could be resolved from BTF alone, which would help on BTF-only kernels without waiting for compilers.

Access records would address no_typeinfo, no_var and no_mem_ops (the record says it is a memory access). no_cuinfo is hand-written asm: out of reach for records too, like the copy routines on the coverage slide. bad_offset and no_sym/no_insn/no_dbginfo/invalid_size folded into two lines to fit.

The source names the field.
The profiler rebuilds a guess.


In the source, every field access names its struct and field. How much of that survives to code generation is your question, not ours.

Peter Zijlstra has asked for per-instruction type information for years; Namhyung agreed it is the ideal.

What we need: access records


  • Address of each load, store or RMW
  • Base type: struct or union, BTF or DWARF
  • Member path and offset
  • Access kind and size
  • "Unknown" when the compiler can't say
  • Descriptive: must not change codegen
One record per memory-accessing instruction, as emitted: instruction address, base type (struct or union, referenced as a BTF or DWARF type), member path through nested types plus offset, access kind (load, store, RMW) and size, and an explicit unknown when the compiler cannot say. Asking for records must not change the generated code.

Precedent: BPF CO-RE already does this



/* .BTF.ext field relocation */
struct bpf_core_relo {
	__u32 insn_off;
	__u32 type_id;
	__u32 access_str_off;
	enum bpf_core_relo_kind kind;
};
  • Emitted by clang and GCC for BPF, marked accesses
  • Instruction → type + member: what perf needs
  • For native code: only describe what was generated

Does the compiler still know this?


  • The source names a type and field for each access
  • Still known late enough to emit per instruction?
  • Kernel constraint: built with -fno-strict-aliasing
  • Whatever produces the records must work with that
Deliberately a question: the people in the room know where this lives in GCC and LLVM.

Coverage: be explicit about the gaps


  • Inline asm memory operands: atomics, locks
  • memcpy, copy_user: perf could use the caller
  • One insn, several fields: range or unknown
  • Honest gaps beat confident guesses

Records first, disassembly stays


  • Useful today, improving on x86, PowerPC and arm64
  • Compiler records: used first, when present
  • Disassembly: when records are absent or not enough
  • Old kernels, modules, toolchains, userspace

Two resolvers, cross-checked


  • 'perf test': resolve the same samples both ways
  • Differences get fixed, on whichever side is wrong
  • Only one method can do it? Suppress, compare rest
  • Like pahole's btfdiff: BTF vs DWARF
  • Both stay valid, both keep improving
btfdiff pretty-prints every type from DWARF and from BTF and diffs the two, suppressing what only DWARF can express. Same idea here: compiler records vs disassembly-based resolution on the same perf.data.

Open questions for this room


  • Encoding: BTF like CO-RE, or DWARF? Either works
  • Size: separate, strippable section, like BTF
  • Inlining: records describe the final instructions
  • One format from GCC and LLVM, opt-in via a flag
