How a sample becomes a type


  • Sample IP → instruction → memory operand
  • PC-relative or absolute: the global variable
  • Else: DWARF variable in that register, by scope
  • Else: replay basic blocks up to the sample
  • x86 and PowerPC; arm64 in review
  • DWARF variables seed register and stack types
From tools/perf/util/annotate-data.c: find_data_type_die() does the direct DWARF match, find_data_type_block() builds basic blocks from each scope start to the sample, innermost scope first, and find_data_type_insn() replays them with update_var_state()/update_insn_state(). percpu: %gs-relative immediates and a tracked percpu base, looked up in DWARF globals. arch_supports_insn_tracking(): x86 and PowerPC only today.

Idea: "sampling" more members


  • Today: only the sampled operand counts
  • "No samples" is not "never accessed"
  • Idea, not implemented: walk the whole block
  • Entry to first branch after the sample: all ran

movl 0xe8(%rbx), %eax   ; +232 sk_ll_usec <- inferred, never sampled
...
movl 0xf4(%rbx), %edx   ; +244 sk_rcvbuf  <- SAMPLED (PEBS/IBS here)
...                     ; straight-line: all executed
jne  .slow_path         ; first branch: stop here
perf would do it: it has the .text open and replays instructions anyway. Prior art: TypeCraft (OSDI 26, section 7.1) already looks at the adjacent memory instructions in the same function as each sampled PC to find other fields of the same type accessed there, and uses that, weighted by hotness, as field affinity for reordering. The idea here takes that into perf proper, during the instruction replay, and adds the instance (data address) when the base register is the same.

Inferred: type vs instance


  • Same base register, unchanged: same instance
  • Its data address follows: sample addr ± offsets
  • Those can feed false sharing and co-access
  • Other base registers: other objects, no address
  • Those give type coverage only
  • Period: same executions, not same event cost
Not implemented yet. An access through the same base register as the sampled one, with the register unchanged in between, is the same object: its data address is the sampled address adjusted by the difference in displacement, so it can take part in instance-based analysis (false sharing, co-access on the same instance). Accesses through other registers touch other objects whose address we do not have: they only add to type coverage. Period: an inferred access in the same straight-line block executed as often as the sampled one, so the sample period transfers as an execution count. It does not transfer as event cost: with mem-loads,ldlat=30 the sampled load qualified, the inferred one may not have (often it hits the line the sampled access brought in), and the latency weight belongs to the sampled instruction only.

  • JSON: direction from the instruction
  • The instruction was right
  • The kernel filled data_src wrong
  • Still does on the E-core PMU: fix not posted yet

The nine disagreeing samples: the CTF producer took load/store direction from the data_src field the kernel reports, the JSON producer from the decoded instruction. Code patched at runtime


  • The kernel rewrites its code, at boot and later
  • Patching can happen at any time
  • perf disassembles vmlinux as built, not as running
  • Samples on patched code: wrong type, or none
  • TEXT_POKE records: the code at sample time
  • Needed: records for patches before recording
Details for questions. An operand-equality test written to drop the nine direction samples flagged many more on the next capture, mostly at plain disp(%rip) sites patched at boot, with _raw_spin_unlock the largest single source (pin the numbers to one named capture). Example: statically a call *pv_ops_lock+0x8(%rip), one fixed operand address; at runtime a native per-instance unlock store, so every store was attributed to pv_ops, which is never touched, and a bogus attribution looks like a good one. bad_addr becomes a metric: how much of a profile is disassembled from text that never ran. The kernel already emits PERF_RECORD_TEXT_POKE for live patches and machine__process_text_poke() updates the DSO data cache that the capstone and LLVM backends read; what is missing is records for patches made before perf record started. The objdump backend reads vmlinux directly and never sees pokes.

What layout changes buy


  • struct sock: sk_drops moved: UDP flood +20%
  • struct sock: sk_peek_off moved: TCP_RR +4-5%
  • TypeCraft: cfs_rq->tg->se[cpu] pointer chasing
  • Fix: co-locate, percpu, drop the array
  • Kernel LLC misses -33%, stress-ng ops/s +8.8%
struct sock: fields of the same hot path share a cacheline (the __cacheline_group_begin__sock_write_rx markers in pahole -C sock). 2016: sk_drops moved away, UDP flood +20%. 2024: sk_peek_off moved for TCP SO_PEEK_OFF, TCP_RR +4-5%. TypeCraft scheduler work merged in v7.0 (Zecheng Li, Google/NCSU): embed sched_entity in cfs_rq, per-CPU cfs_rq allocation, remove the task_group->se pointer array. From the paper (OSDI 26, section 7.2), 24-core Intel w7-2495X, Linux 6.17: kernel LLC misses a further -33% on their schbench cfs_rq microbenchmark, on top of field reordering; embedding alone regressed LLC misses by over 50% from 1024-byte slab alignment, fixed by the per-CPU allocator; the Intel kernel test robot reported +8.8% on stress-ng.session.ops_per_sec. Earlier: rq reorder -5.1% kernel cycles, cfs_rq reorder -26.4% kernel LLC misses. MySQL: LLC misses down up to 14.9%, peak TPS +1.8%.

What compilers give us today


  • -Wpadded, and struct layout dumps in both
  • No profile-driven struct layout upstream
  • GCC had struct reorg once: what did we learn?
  • BOLT/AutoFDO/Propeller: code, not data layout
  • LLVM TBAA: typed accesses, not emitted
  • MemProf: heap; RFC: vtables for PGO
  • Native (!BPF): no access types in the binary
-Wpadded (GCC and clang) warns when padding is added to a structure, to align a member or the whole struct: static layout only, no notion of which fields are hot. GCC struct reorg: -fipa-struct-reorg by Olga Golovanevsky (IBM), 2006-2007, profile-based or static, whole program only; removed in GCC 4.8 (2012) because it did not always work correctly and did not work with LTO (link on the slide: GCC 4.8 release notes). Revived out of tree in 2020 as LTO type-escape analysis plus dead field elimination (Erick Ochoa, ARM vendor branch arm-struct-reorg-wip): https://www.mail-archive.com/gcc@gcc.gnu.org/msg92675.html. TBAA link: the LangRef tbaa metadata section (struct path TBAA: type descriptors and access tags); the source-level description is the comment at the top of llvm/lib/Analysis/TypeBasedAliasAnalysis.cpp. Related, from 2021: in the discussion of LLVM review D101185 (https://reviews.llvm.org/D101185), the LLVM alias analysis call concluded they should move away from tbaa metadata towards reusable type metadata, with tbaa as a subset: close to what we ask for. Type-based alias info: loads/stores carry base type, access type and offset in LLVM, used for optimization and not written to the binary; ask whether GCC has an equivalent. Dynamic type profiling RFC: Mingming, Teresa, David, Snehasish (Google), Nov 1 2023, https://discourse.llvm.org/t/rfc-dynamic-type-profiling-and-optimizations-in-llvm/74600, instrumentation-based, for indirect call promotion.

Seeing it: TBAA in clang



$ cat tbaa.c
struct s { int a; long b; };
long f(struct s *p) { return p->b; }

$ clang -O2 -S -emit-llvm tbaa.c -o -     # trimmed
  %2 = getelementptr inbounds nuw i8, ptr %0, i64 8
  %3 = load i64, ptr %2, align 8, !tbaa !7
!7 = !{!8, !9, i64 8}                  ; tag: base, access, offset
!8 = !{!"s", !4, i64 0, !9, i64 8}     ; struct s: int @0, long @8
!9 = !{!"long", !5, i64 0}

$ clang -O2 -fno-strict-aliasing -S -emit-llvm tbaa.c -o -     # trimmed
  %2 = getelementptr inbounds nuw i8, ptr %0, i64 8
  %3 = load i64, ptr %2, align 8
  • Access tag: base type, access type, offset
  • Byte GEP: only the tag still names struct s
  • -fno-strict-aliasing: no tags at all
Records live in llvm/lib/Analysis/TypeBasedAliasAnalysis.cpp (format comment at the top), built by clang/lib/CodeGen/CodeGenTBAA.cpp, gated in clang/lib/CodeGen/CodeGenModule.cpp on optimization enabled and RelaxedAliasing off. The type info exists, but only as a license for alias analysis: there is no descriptive-only mode, which is why the kernel gets none of it. Output from clang 22.1.8 (Fedora 44); the ; comments on the metadata lines are annotations added for the slide. Note the getelementptr is on i8 with a byte offset: the address computation no longer mentions struct s, so the TBAA tag is the only place the type survives. Why the GEP is on i8: since the canonicalization by Nikita Popov (llvm-project PR 68882), getelementptr with constant indices is rewritten to i8 with a byte offset, a first step of the RFC replacing getelementptr with ptradd (linked on the slide). The struct type is no longer carried by the address computation. There has since been LLVM discussion about carrying GEP type traversal information again (an RFC on adding instructions for it, and a Type based GEP plans thread): worth asking about in the room. With -fno-strict-aliasing the same IR comes out with no !tbaa on the load and no TBAA metadata in the module at all (even !llvm.errno.tbaa is gone): the load is just 8 bytes at offset 8 from a pointer.

Seeing it: MEM_EXPR in GCC



$ gcc -O2 -fdump-rtl-final -c tbaa.c       # tbaa.c.370r.final, trimmed
(insn:TI 6 3 12 2 (set (reg:DI 0 ax [orig:101 p_2(D)->b ] [101])
        (mem:DI (plus:DI (reg/f:DI 5 di [orig:102 p ] [102])
                (const_int 8 [0x8])) [1 p_2(D)->b+0 S8 A64]))
;; [alias set  MEM_EXPR+MEM_OFFSET  size  align]

$ gcc -O2 -fno-strict-aliasing -fdump-rtl-final -c tbaa.c   # same mem
        (mem:DI (plus:DI (reg/f:DI 5 di [orig:102 p ] [102])
                (const_int 8 [0x8])) [1 p_2(D)->b+0 S8 A64])
  • At final: field, offset, size, alignment
  • Registers too: %rdi holds p, %rax holds p->b
  • -fno-strict-aliasing: identical, field kept
GCC RTL memory attributes (gcc/rtl.h, set in gcc/emit-rtl.cc, set_mem_attributes): MEM_ALIAS_SET, MEM_EXPR (can be a COMPONENT_REF: the field reference), MEM_OFFSET, MEM_SIZE, MEM_ALIGN. They are still there in the final RTL pass. REG_EXPR/REG_OFFSET on registers record what each register holds, which is what perf instruction tracking reconstructs. GCC already emits BTF for native targets (-gbtf together with DWARF on x86), and has .BTF.ext CO-RE relocation output for BPF in gcc/config/bpf/btfext-out.cc and core-builtins.cc. With -fno-strict-aliasing the final RTL is identical, alias set number included: the MEM_EXPR is still there under the kernel build flags, unlike clang, which drops all TBAA. Why the alias set still prints as 1 is a good question for the GCC people: presumably the flag is honored when alias sets are compared rather than by clearing them. Question for the room: could a late pass read MEM_EXPR/MEM_OFFSET and emit .BTF.ext-style access records for native targets, independent of -fno-strict-aliasing? The ;; legend line is an annotation added for the slide. Reconstruction has a ceiling


  • Optimized code: DWARF loses register variables
  • Branches and loops blur what a register holds
  • Several matching types? A heuristic picks one
  • container_of offsets, casts, void *: no type
  • Needs full DWARF: production kernels ship BTF
  • Per arch: arm64 tracking is 15 patches
  • find /: unknown for 17.95% loads, 27.49% stores
is_better_type() in annotate-data.c is the heuristic; update_var_state() handles container_of only for offset 0 (the copy-back case). perf data-type profiling does not use BTF today (no BTF in annotate-data.c). Globals and percpu variables could be resolved from BTF alone, which would help on BTF-only kernels without waiting for compilers.

What we need: access records


  • Address of each load, store or RMW
  • Base type: struct or union, BTF or DWARF
  • Member path and offset
  • Access kind and size
  • "Unknown" when the compiler can't say
  • Descriptive: must not change codegen
One record per memory-accessing instruction, as emitted: instruction address, base type (struct or union, referenced as a BTF or DWARF type), member path through nested types plus offset, access kind (load, store, RMW) and size, and an explicit unknown when the compiler cannot say. Asking for records must not change the generated code.

Coverage: explicit gaps


  • Inline asm memory operands: atomics, locks

  • Honest gaps beat confident guesses

Records first, cross-checked


  • Compiler records: used first, when present
  • Disassembly: when absent or not enough
  • perf test: resolve the same samples both ways
  • Differences fixed on whichever side is wrong
  • Only one can do it? Suppress, compare the rest
  • Like pahole's btfdiff: BTF vs DWARF
Disassembly-based resolution is useful today and improving on x86, PowerPC and arm64, and stays for binaries without records: old kernels and distros, modules, older toolchains, userspace. btfdiff pretty-prints every type from DWARF and from BTF and diffs the two, suppressing what only DWARF can express. Same idea here: compiler records vs disassembly-based resolution on the same perf.data. Both stay valid, both keep improving.

When several types match


  • Inlining: caller and callee see the same register
  • container_of(): member pointer vs enclosing struct
  • Offset 0: a struct and its first member
  • typedef vs the struct it names
  • Replay: a slot already typed, DWARF offers another
  • Rule: largest offset, then is_better_type()
Backup slide, linked from the ceiling slide. find_data_type_die() walks the DWARF scopes enclosing the sampled PC, innermost inlined block out to the function, asking which variable lives in the base register at this PC; when more than one scope answers there are candidates. Inlining: the TypeCraft paper (section 3.4) example passes a->b to an inlined callee: in the caller scope the register is a, so the access is struct A member b; in the callee scope it is only the parameter, typed as the type of b. container_of(): one variable sees a struct list_head *, another the enclosing struct, as register plus offset in DWARF. Offset 0: struct foo *f and &f->first are the same address. typedef: same layout, different name. Replay: update_var_state() faces the same choice for registers and stack slots. Rule: keep the candidate with the largest access offset (usually the outermost struct); on ties is_better_type() prefers a pointer, then the bigger pointed-to type, then struct or union over scalar, then a typedef. Nothing in the binary says which view is right; access records would.
